# 02 · 分层记忆：L1/L2/L3 与触发表

## 为什么要分层

一次性注入通道（工具每会话自动塞进上下文的文件）有两个硬约束：**容量有限**（常见 4000 字符级截断）和**每 token 都烧钱**。所以不能把所有记忆都塞进去。

答案是把记忆按"被读到的概率"分层：

| 层 | 内容 | 读法 | 预算 |
|---|---|---|---|
| **L1 热记忆** | 索引 + 硬线（触发表、铁律、当前状态） | 争取每会话可见（经注入通道或开工第一条指令） | **≤3300 字符**（为注入截断留余量） |
| **L2 明细** | 分领域档案：工作规范 / 环境与工具 / 用户画像…… | **命中才读**，读完就干活 | 每个文件独立，几十 KB 无所谓 |
| **L3 归档** | 历史决策全文、证据链、归档纪要 | grep 查询，别通读 | 不限 |

**L1 是"目录页"，L2 是"正文"，L3 是"档案馆"。** L1 里严禁放细节——它曾经 70KB，结果注入通道只进前 4000 字符，后面的内容写了等于没写。这是本体系最贵的教训。

## 触发表：命中即必读

L1 的核心是一张表。规矩只有一条：**命中下表 → 第一个动作就是把那个文件读进来，再动手。跳过读取＝违规。**

```markdown
| 触发 | 必读 |
|---|---|
| 交付 / 收尾（改过文件、生成、下载、安装） | L2-work-conventions.md §交付报告 |
| 交接工作 / 续做任务 | 工作区根目录 HANDOFF.md |
| 跑命令 / 写脚本 / 改系统 / 排网络 | L2-environment.md |
| 调查 / 评审 / 讨论收尾，或主人说"出纪要" | 写纪要到 _ai_shared/meeting-minutes/ |
| 要具体数字、路径、证据链 | L3/archive.md（grep，别通读） |
```

设计要点：

- **触发词写"任务类型"，不写"关键词"**——AI 判断"这活属于哪类"比"这句话含不含某词"可靠
- **每行一个动作**（读哪个文件），不写"相关内容见……"这种含糊话
- 表要短。L1 超预算时，先砍 L1 的非索引内容，永远不砍触发行

## 同步脚本：一份源文件，多个注入点

各工具的注入文件不同（工具 A 读 `~/.toolA/AGENTS.md`，工具 B 读自己的用户目录下 `MEMORY.md`……）。**手写多份必然漂移**——解法是一份源文件 + 一个同步脚本：

```bash
python sync_memory.py
```

脚本做两件事（完整实现见 [templates/sync_memory.py](../templates/sync_memory.py)，55 行，零依赖）：

1. 读共享源文件（`project-rules.md`、`L1-hot-memory.md`）
2. 包上 `<!-- SYNC:BEGIN -->...<!-- SYNC:END -->` 标记块，写入各工具的注入目标文件；已有标记块则原地替换

**铁律：永远别手改目标文件里的 SYNC 块**——下次同步会被覆盖。要改就改源文件，再跑脚本。

## 预算管理

- L1 写完跑一次同步，看脚本输出的字符数
- 给自己定两条线：**预警线**（本机用 3600/3900）、**死线**（注入截断值 3900）
- 超预警线：把最旧的条目挪去 L2，L1 只留一行指针
- 定期体检（见 [04-protocols.md](04-protocols.md)），把"超预算再瘦身"变成制度而不是记忆

## 热文件并发保护

多个 AI 同时活着，共享文件（L1、项目规则）就是并发写入点。实测事故：两个 AI 在同一小时内先后改同一个 L1，后者读的是旧版。

三条规矩（写进项目规则，让每家都守）：

1. 改共享源文件前**必须重读最新版**
2. 只做**增量插入**，禁止整篇重写（Write 覆盖会把别家刚写的内容抹掉）
3. 改完立即跑同步脚本

## 快照纪律

- 带时效的事实（余额、有效期、临时状态）**必须带日期**：`XX（2026-11-07 实测）`
- 引用任何记忆/纪要/报告前，先核对是否仍成立——**文件是快照不是实时**
- 过期结论不当现行事实用。这需要制度化（定期体检扫过期条目），不能靠 AI 自觉
