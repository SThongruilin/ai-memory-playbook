# 03 · 身份文件三件套与注入通道

## 三件套的分工

| 文件 | 放什么 | 不放什么 |
|---|---|---|
| **SOUL.md** | 灵魂层：我是谁、价值观、说话方式、最高频铁律（每条一行） | 操作细则、路径清单、流程步骤 |
| **IDENTITY.md** | 操作层：交付流程细则、记忆路径清单、行为准则、场景切换规则 | 价值观长篇论述 |
| **USER.md** | 用户画像：称呼、偏好、协作边界、长期跟踪项 | 临时状态、会过时的细节 |

设计逻辑：**SOUL 管不变的东西，IDENTITY 管随流程迭代的东西，USER 管关于"人"的事实。** 三者都会被频繁注入，所以每一条都要精炼——重复是浪费注入预算，但**最高频的 3~5 条硬规则在两个文件里各出现一次是有意的双保险**（规则没送到是执行失败的头号根因）。

## 注入优先级链（通用模型）

```
系统提示（工具内置）
  > 身份层（SOUL / IDENTITY / USER —— 每会话自动注入，最可靠）
  > 项目级规则（AGENTS.md / project-rules —— 多工具可共用同一份）
  > 记忆索引（MEMORY.md 类 —— 各工具差异最大、可靠性最差的一层）
  > 会话中按需读取（L2/L3 —— 由触发表驱动）
```

两个实战结论：

1. **硬线必须写进身份层**。记忆索引层的注入往往不稳定（实测某工具只有 2/10 会话注入 MEMORY.md）——"规则没送到"是执行失败的常见根因。
2. **项目级规则文件是所有工具的共用锚点**。大多数 Agent 类工具都会读工作区根目录的 `AGENTS.md` 类文件；用同步脚本把共享规则分发进去，改一处、三家生效。

## 测绘你自己的工具：四个问题

各工具实现差异很大，别猜，**实测**。对每个工具开新会话，逐个验证：

1. **它每会话自动注入哪些文件？** —— 问它"你的系统上下文里有哪些关于我的描述？"，或直接在疑似文件里埋一句独特标记（如 `<!--canary-2026-xx-xx-->`），下次问它能不能看到
2. **注入截断阈值是多少？** —— 在注入文件尾部放一句"最后一行测试"，不断加长直到它答不出，就摸到了阈值
3. **注入稳定性如何？** —— 抽 10 个会话看某文件是否到场（例：10/10 表示可靠，2/10 表示别指望它）
4. **会话正文存哪？** —— 找到对话落盘文件（通常是工作区转义目录下的 `.jsonl`），做跨会话审计时用

把测绘结果写成一张表，放在 L2 里，这就是你的"注入机制地图"。**工具升级会改变注入行为——日期性条目要带日期，定期体检时复核。**

## 三条快照纪律

1. **时效性标注**：带日期的事实必须写日期；引用前核对是否仍成立
2. **备份纪律**：改身份文件前先 `原名.bak-日期` 备份；有 GUI 设置入口的工具，以设置为权威入口，手动改文件后要验证是否被设置覆盖
3. **脱敏红线**：身份文件、记忆、报告、纪要，一律不落 cookie / token / 密码 / API key 明文，只写"已配置"和存放位置
