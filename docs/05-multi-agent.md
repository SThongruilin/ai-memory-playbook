# 05 · 多 AI 协作：共享层、跨家审计、并发保护

前提：你同时用 2 个以上 AI 工具，各家的会话记忆**互不相通**（模型不同、进程不同、存储不同）。它们之间的"公共地带"只有一个——**磁盘上的共享层**。

## 1. 共享层原则

> **涉及多家的发现/变更，必须落共享层（L2/项目规则），禁止只写自家记忆。**

这条解决一个隐蔽问题：AI-A 发现了某个机制/踩了某个坑，只写进自己的私有记忆——AI-B 永远不知道，下次踩同一个坑。既然你们让它们协作，知识就该进公共硬盘。

反过来，**共享层的权威声明要防漂移**：同一份信息（如用户画像）在多家各有副本时，必须指定唯一权威源（如"L2-用户画像.md 为准，冲突以它为准，更新只改它"），并把声明写进每家的副本顶部。

## 2. 跨家审计：找到别家的对话

交接工作的最高效形态不是"你总结给我听"，而是**直接读对方的会话原文**——包括它收到的注入、它的思考过程、它的工具调用。各工具的会话落盘位置不同，但套路一致：

| 常见位置模式 | 例子 |
|---|---|
| `~/.工具名/projects/<工作目录转义>/<sessionId>.jsonl` | 若干编码 Agent，明文 JSONL |
| `~/.工具名/sessions/<工作目录转义>/<sessionId>/session.vN.jsonl.zstd` | 部分框架，zstd 压缩 |
| `~/.工具名/<sessionId>/rollout/*.jsonl` | 明文，全量模型输入输出 |

**JSONL 结构基本一致**：每行一个事件——用户/助手消息、思考（reasoning）、工具调用与结果、会话元数据。**第一条 user 消息里通常内嵌当次全部注入原文**——这是审计"对方到底收到了什么规则"的权威证据。

**四个假对话陷阱**（实测踩过）：

- `sessions/*.json` 可能只是**进程心跳**（pid/heartbeat），不是对话
- `logs/*.log` 是运行日志，**没有对话正文**
- 主数据库（SQLite）可能**只有会话元数据**（标题/时间/工作目录），正文在 jsonl
- 以对话命名的工作目录可能是**空的**

**审计流程**：定位最新会话文件（按修改时间）→ 先读最后几条助手消息（那是结论）→ 需要证据再回看注入原文和工具调用 → 引用时注明来源家、sessionId、时间。

## 3. 并发写保护

多个 AI 同时活着，共享文件就是并发写入点。三条规矩（写进项目规则让每家遵守）：

1. 改共享源文件前**必须重读最新版**（工具层的"文件已变更"报错是保护不是阻碍）
2. 只做**增量插入**，禁止整篇重写——Write 整篇覆盖会把别家刚写入的内容抹掉
3. 改完立即跑同步脚本

## 4. 身份文件纪律（多 AI 版）

- 每家的身份文件改动前先 `原名.bak-日期` 备份
- 有 GUI 设置入口的，以**设置为权威入口**；手动改文件后验证是否被设置覆盖
- 从对话/网页复制路径到设置时，警惕 `\下划线` 组合的反斜杠被渲染层吃掉——**配置里的路径一律用正斜杠**
- 改完 24h 内开新会话做一次生效验证（问询法，见 [03-identity-files.md](03-identity-files.md) 的自检表）

## 5. 分工建议（按能力，不按名分）

多家的价值在于能力互补：终端 Agent 适合写码/逆向/文件手术，桌面助手适合 GUI 自动化/值守/定时任务，Agent 框架适合装插件联网干活。**不要给三家立固定分工表**（活是临场决策），但要立"能力地图"：每家能干什么、有什么硬限制，写在 L2 里，派活时查。
